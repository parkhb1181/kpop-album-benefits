# 뮤직플랜트 105초 — 무엇을 계측했고 원인이 뭐였나

`docs/38-수집단계-인계.md`의 **4번**(rebuild 20분 타임아웃) 조사 기록이다.
작성 2026-08-28 · 코드 레인.

결론부터 — **뮤직플랜트가 느린 게 아니었다.** 연결이 안 되는 상황에서
우리 재시도 가드가 그걸 못 알아채고 비용을 3배로 불린 것이고,
거기에 `searchWide`의 폴백 질의가 곱해졌다.

---

## 1. 105초는 상수가 아니었다 — 35초의 배수다

인계 문서는 105.2 / 105.3 / 105.2가 "거의 상수"라는 걸 단서로 짚었다. 맞는 관찰인데,
상수인 건 105초가 아니라 **질의 한 건당 35초**였다.

문서가 "`musicplant.mjs`는 호출이 한 번뿐"이라고 본 건 파일 기준이고,
실제로 부르는 건 [`build.mjs`](../build.mjs)의 `searchWide()`다. 이게 결과가 0건이면
아티스트명 변형 → 앨범명 단독 → 발매일 폴백까지 질의를 반복한다.

`out/data/*.json`에서 실제 `artistEn`을 꺼내 질의 수를 세면 정확히 맞는다:

| 앨범 | `artistEn` | `nameVariants` | 질의 수 | 관측 | ÷질의 |
|---|---|:-:|:-:|:-:|:-:|
| TUIDE | `TUIDE` | 1 | 3 | 105.3s | **35.1** |
| TAEMIN | `TAEMIN` | 1 | 3 | 105.2s | **35.1** |
| NCT | `NCT 127` | 1 | 3 | 105.2s | **35.1** |
| i-dle | `i-dle (아이들)` | 3 | 7 | 245s | **35.0** |

`i-dle`만 245초였던 것도 이걸로 설명된다 — 괄호 병기 때문에 이름 후보가 3개라
질의가 7회다. **설명 안 되는 숫자가 아니라, 세는 단위를 잘못 잡고 있었다.**

## 2. 그래서 "getText 한 건이 왜 35초인가"

`getText`는 타임아웃 15초 + `TimeoutError`면 즉시 break라 최대 15초여야 한다.
라우팅되지 않는 IP(SYN 블랙홀)로 재현했다 — 러너에서 연결이 안 되는 상황과 같은 경로다.

```
raw fetch  11.30s
  e.name        = TypeError            ← 여기만 보면 절대 못 찾는다
  e.code        = undefined
  e.cause.name  = ConnectTimeoutError
  e.cause.code  = UND_ERR_CONNECT_TIMEOUT
  e.cause.message = Connect Timeout Error (attempted address: 10.255.255.1:80, timeout: 10000ms)

getText    35.67s
```

**35.67초.** 관측된 35.0~35.1초와 일치한다. 기전은 셋이 겹친 것이다.

1. **undici의 connect 타임아웃이 10초**로, 우리 `AbortSignal.timeout(15000)`보다
   **먼저** 터진다. 그래서 15초 타임아웃은 영영 발동하지 않는다.
2. 그때 던져지는 건 `TypeError: fetch failed`이고, `ConnectTimeoutError`는
   **`e.cause`에 숨어 있다.** `e.name === 'TimeoutError'`만 보던 가드는 안 걸린다.
3. 가드가 안 걸리니 "무응답은 재시도해도 무응답"이라는 **주석과 정반대로** 3회를 다 쓴다.
   `3 × 11.3초 + 백오프(0.6+1.2+1.8) ≈ 35.6초`.

## 3. 되먹임 — 막히면 질의가 늘어난다

이게 왜 20분까지 갔는지의 나머지 절반이다.

정상일 때 `searchWide`는 결과가 나오는 질의에서 멈춘다. 그런데 **막히면 결과가 0건이 되고,
0건이니 폴백 질의가 전부 돈다.** 앨범당 질의가 1~2회에서 3~7회로 뛰고, 13앨범이면
죽은 몰 하나에 **39~91번**을 두드리게 된다. 막힘 → 질의 폭증 → 더 오래 막힘이다.

`8분 21초 ↔ 27분 43초`로 갈렸던 것도 이 구조 위에서 보면 자연스럽다 —
연결이 언제 끊기느냐에 따라 증폭이 걸리느냐 마느냐가 갈린다.

## 4. 러너 계측 결과

run [33092670290](https://github.com/parkhb1181/kpop-album-benefits/actions/runs/33092670290)
· 2026-08-28 01:20 KST · 출구 IP `135.119.39.18`(Azure) · 러너에 IPv6 경로 없음.

**이 회차에는 재현되지 않았다.** 뮤직플랜트가 정상으로 열렸다.

| | 뮤직플랜트 | 알라딘(대조군) |
|---|---|---|
| DNS | A 1건 `121.254.238.142` · AAAA 없음 | A 4건 |
| TCP | ✓ 0.16s | ✓ 0.02s |
| TLS | ✓ 1.72s | ✓ 0.11s |
| 연속 20건 | `200` × 20 · 1.1~2.4s | `200` × 20 · 0.5~1.5s |

재현은 못 했지만 **가설 셋이 반증됐다.** 이게 이번 계측의 소득이다.

- **요청 누적으로 막히는 게 아니다.** 20건을 연달아 쳐도 안 무너진다. 즉 1건째부터
  막히거나 아예 안 막히거나이고, **우리 쪽 요청 수를 줄이는 걸로는 못 막는다.**
  회로 차단기가 맞는 대응이라는 근거다 — 줄일 수 없다면 빨리 포기하는 수밖에 없다.
- **IPv6 문제가 아니다.** 뮤직플랜트에 AAAA 레코드가 없고 러너에도 IPv6 경로가 없다.
  양쪽 다 IPv4 단독이라 happy-eyeballs 지연 가설은 성립하지 않는다.
- **DNS가 아니다.** 0.7초 안에 해석된다.

러너에서 뮤직플랜트가 로컬보다 2배쯤 느리긴 하다(1.1~2.4초 vs 0.2~1.1초). 거리 차이
수준이고 105초와는 무관하다.

**남은 가설** — 실패 창에서는 SYN 자체가 안 돌아온다(connect 타임아웃이 근거).
그 조건은 아직 못 잡았다. 시간대나 러너 IP 대역이 유력하지만 **추측이고, 결론으로
적지 않는다.**

### 실패 창을 앞으로 어떻게 잡나 — 따로 샘플러를 만들 필요 없다

회로 차단기가 걸리면 rebuild 로그 끝에 이 줄이 찍힌다:

```
  ⚠ www.musicplant.co.kr — 연결 불가로 이 빌드에서 제외했습니다 (이후 요청 N건 건너뜀)
```

하루 두 번 도는 rebuild가 그대로 샘플러다. **그 줄이 찍힌 회차의 시각과 러너 IP를
모으면 조건이 보인다.** 지금 당장 캘린더를 채우려고 probe를 반복해 돌리는 건
Actions 시간만 태우고 같은 데이터를 준다.

그 줄이 찍히는 회차는 그 판매처 데이터가 **없는 게 아니라 못 받은 것**이다.

## 5. 고친 것

### `src/fetchx.mjs`

- **`e.cause`까지 본다.** `ConnectTimeoutError` · `HeadersTimeoutError` ·
  `BodyTimeoutError` · `UND_ERR_*` · `ETIMEDOUT`을 전부 "닿지 않음"으로 판정해
  재시도를 멈춘다. 한 건 35.7초 → **10.6초**.
- **호스트별 회로 차단기.** 연속 3회 **또는 누적 60초**를 연결 대기로 태운 호스트는
  이 빌드에서 포기한다.
  - 연속 3회 = 앨범 하나가 쓰는 질의 수. 한 앨범치 증거는 보고 판단한다.
  - 누적 60초를 같이 두는 이유 — 지연이 **간헐적**이라 드문드문 성공하면 연속
    카운터가 초기화돼 차단기가 영영 안 걸린다. 막으려는 건 총 소요 시간이다.
  - 응답이 한 번이라도 오면 연속 카운터는 초기화한다. 일시적 흔들림으로 몰을 버리지 않는다.
- 마지막 시도 뒤의 백오프 대기를 없앴다 (그냥 버리는 시간이었다).
- 에러 메시지에 `cause`의 원인을 적는다. `fetch failed`만 남으면 다음 사람이 또 못 찾는다.

**실측 (블랙홀 IP에 7회 = searchWide 최대 질의 수):**

```
  #1   10.65s  ConnectTimeoutError: Connect Timeout Error …
  #2   10.61s  ConnectTimeoutError: …
  #3   10.60s  ConnectTimeoutError: …
  #4    0.00s  연결 불가로 건너뜀 (연속 3회 실패)
  #5    0.00s  …
  #6    0.00s
  #7    0.00s
  합계 31.85s   (수정 전이라면 7 × 35.7 = 250s)
```

살아 있는 호스트는 영향 없음 (뮤직플랜트 `태민` 0.73s / 20건, `TUIDE` 0.63s / 7건).

**닿지 않는 몰 하나의 비용이 앨범당 105초에서 빌드 전체 32초로 떨어진다.**

### `build.mjs`

- `searchWide`가 **"0건"과 "질의 전부 실패"를 구분한다.** 전엔 둘 다 `[]`였다.
  그래서 뮤직플랜트가 러너에서 막혔을 때 그 판매처가 페이지에서 조용히 사라졌고,
  화면상으로는 *"이 앨범을 안 판다"* 와 구별되지 않았다.
  이제 전부 실패면 예외를 올리고, 기존 `errors` 경로를 타 [`render.mjs`](../src/render.mjs)의
  "수집 실패" 줄에 나온다. (CLAUDE.md 2번 규칙)
- 빌드 끝에 포기한 호스트를 로그로 남긴다. 조용히 지나가면 다음 사람이
  "그 몰은 원래 안 나온다"고 믿게 된다.

### `probe_net.mjs` + `.github/workflows/probe-net.yml`

러너 전용 계측기. DNS(A/AAAA) → IP별 TCP → TLS → 첫바이트 → 본문을 쪼개 재고,
**연속 호출**로 "1건째부터 막힘(IP 차단)"과 "N건째부터 막힘(요청 폭주)"을 가른다.
알라딘이 대조군이다 — 뮤직플랜트만 느린 건지 러너 전체가 느린 건지 구분하지 못하면
엉뚱한 걸 고치게 된다. `out/`은 건드리지 않는다.

```bash
gh workflow run probe-net.yml -f burst=20
```

## 넘기지 않은 것 — 확인했지만 이번에 안 고친 것

**뮤직플랜트는 공백이 든 복합 질의를 못 받는다.** 위드뮤와 같은 성질이다.

```
  0.39s   20건  "태민"
  0.29s    7건  "PHASE I : Soft Violence"
  0.44s    0건  "태민 PHASE I : Soft Violence"      ← 항상 0건
  0.25s    0건  "TUIDE TUNE & PLAY"
  0.23s    0건  "NCT 127 BLINGY"
```

`searchWide`의 첫 질의는 항상 `"아티스트 앨범명"` 꼴이라 **뮤직플랜트에서는 매번 버려진다.**
정상 빌드에서도 앨범당 2회를 쓴다는 뜻이고, 빌드당 13건이 낭비다.

고치지 않은 이유 — ⓐ 8분↔27분을 가르는 크기가 아니다 ⓑ 질의 순서를 바꾸면 매칭
결과가 달라질 수 있어서, 타임아웃 수정과 같은 커밋에 섞으면 회귀가 생겼을 때
원인을 못 가른다. 별도로 다룰 일이다.

(질의마다 응답이 달라지므로 검색 자체는 살아 있다 — 예스24 같은 "안 변하는 응답" 함정은 아니다.)

## 반증된 것

- **"뮤직플랜트가 느리다"** — 아니다. 응답이 오면 0.2~1.1초다. 문제는 응답이 아예 안 올 때다.
- **"`musicplant.mjs`가 호출을 한 번만 하니 105초는 설명이 안 된다"** — 파일만 보면 맞지만
  호출자가 `searchWide`라 3~7회다. **한 파일 안에서 비용을 세면 안 된다.**
- **"타임아웃 15초 + 즉시 break라 한 건이 105초가 될 수 없다"** — 전제가 틀렸다.
  undici가 10초에 먼저 끊고, 그 에러는 우리 가드에 안 걸린다.

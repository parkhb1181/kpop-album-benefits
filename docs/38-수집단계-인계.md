## 1. HTML 엔티티가 디코딩되지 않아 같은 상품이 갈라진다 — **가장 급함**

### 실측 증거

`out/data/cortis-greengreen.json`에서 **같은 립밤 특전**이 판매처마다 다르게 인코딩된다:

| 판매처 | 상품명에 담긴 것 |
|---|---|
| Ktown4u | `[GREENGREEN] (&#x27;Blue Lips&#x27; 립밤)` |
| 사운드웨이브 | `[GREENGREEN] (&#039;Blue Lips&#039;...)` |
| 알라딘 | `[GREENGREEN] ('Blue Lips' 립밤)` |

세 개가 서로 다른 문자열이라 **버전 키가 세 개로 갈라지고**, 조각마다
"1곳만 판매"라는 잘못된 배지가 붙는다. 실제로는 3곳이 같은 걸 판다.

키에 그대로 남은 잔재:
- `cortis-greengreen` → `editionKey: "x27bluelipsx27lipbalm"`
- `shinee-make-it-hot` → `editionKey: "ohitx27shot"` (원본 `Oh it&#x27;s hot Ver.`)
- `tuide-tune-play` → 상품명 8건에 `TUNE &amp; PLAY`가 그대로 저장돼 있다

### 원인

`src/fetchx.mjs`의 `strip()`이 이름 붙은 엔티티 6개만 처리한다:

```js
.replace(/&nbsp;/g, ' ').replace(/&amp;/g, '&').replace(/&lt;/g, '<')
.replace(/&gt;/g, '>').replace(/&quot;/g, '"').replace(/&#39;/g, "'")
```

빠진 것: `&#x27;`(16진), `&#039;`(0으로 채운 10진), 그 밖의 모든 `&#NNN;` / `&#xHH;`.
그리고 `&amp;`가 저장된 상품명에 남아 있는 걸 보면 **일부 판매처 어댑터는 상품명에
`strip()`을 아예 안 태우고 있다.**

### 프롬프트

```
poc/ 수집 파이프라인에서 HTML 엔티티가 디코딩되지 않아 같은 상품이 여러 버전으로 갈라진다.

증거 (out/data/*.json 실측):
- cortis-greengreen: 같은 'Blue Lips' 립밤 특전을 Ktown4u는 &#x27;로,
  사운드웨이브는 &#039;로, 알라딘은 그냥 '로 준다. 셋이 다른 문자열이라
  editionKey가 갈라지고 조각마다 "1곳만"이라는 틀린 배지가 붙는다.
- editionKey에 남은 잔재: "x27bluelipsx27lipbalm" (cortis-greengreen),
  "ohitx27shot" (shinee-make-it-hot, 원본 "Oh it&#x27;s hot Ver.")
- tuide-tune-play: 상품명 8건에 "TUNE &amp; PLAY"가 디코딩 안 된 채 저장돼 있다.

할 일:
1. src/fetchx.mjs의 strip()에 **숫자 엔티티 일반 처리**를 추가하라.
   &#39; 하나만 하드코딩하지 말고 &#NNN; 과 &#xHH; 를 모두 코드포인트로 변환할 것.
   (&#x27; &#039; &#8217; &#8220; 등이 전부 실제로 나온다)
2. 상품명(title)이 strip()을 안 거치는 어댑터가 있는지 확인하고 전부 태워라.
   src/ktown4u.mjs, aladin.mjs, soundwave.mjs, withmuu.mjs, musicplant.mjs,
   applemusic.mjs, weverse.mjs, yes24.mjs 전부 점검할 것.
   ("TUNE &amp; PLAY"가 남아 있다는 건 최소 한 곳은 안 태운다는 뜻이다)
3. 버전 키 정규화는 **디코딩 후**에 돌아야 한다. 순서가 뒤바뀌면 지금과 똑같이
   x27이 키에 박힌다.

절대 하지 말 것:
- "unnaturalvergazedverbreak"를 깨진 값으로 보고 고치지 마라. 이건 실제
  3종 세트다 (edition: "Unnatural+Gazed+Break ver."). 정상 데이터다.
- src/render.mjs는 건드리지 마라. 프론트 담당이 따로 있다.

검증: 고친 뒤 재수집해서 out/data/*.json의 editionKey에 x27/x2f/amp/quot/#039
가 하나도 없어야 하고, cortis-greengreen의 립밤 특전이 한 키로 합쳐져야 한다.
```

## 2. ~~`benefitImage`가 안내 배너를 가리킨다~~ — **철회. 틀린 진단이었다**

**이 항목은 넘기지 마라. 수집 쪽은 지금 맞게 동작하고 있다.**

프론트 담당(나)이 이미지를 열어보지 않고 치수만 보고 "공지문"이라고 단정했다.
2026-08-27에 실제로 열어보고 반증됐다.

`nct-127-blingy` 위버스샵 `benefitImage`(1000×6140)를 내려받아 확인한 내용:

- `'Weverse Global x STUDIO CHOOM' 특전 증정 이벤트` 제목
- **`증정 상품 — 스튜디오 춤 착장 미공개 셀카 포토카드 5종 중 랜덤 1종`**
- **실제 포토카드 5장 사진**
- 응모 기간(8/25 17:00 ~ 8/30 23:59), 응모 대상, 유의사항

이 페이지가 답하려는 질문("이 판매처에서 사면 뭘 받나")에 정확히 답하는 자료다.
대신 쓰라고 적었던 720×1080은 **구성품 시트**(포스터·스티커·CD-R 목록)라,
그걸 `benefitImage`로 올리면 구성품이 "위버스샵 특전"으로 표시된다.
720×1575는 보도자료 텍스트 페이지이고 비율 2.19라 2.4 기준에 걸리지도 않는다.
`82major-heat` 720×2328도 열어보니 `Pre-order Gift` 안내에 셀피 포토카드가 찍혀 있었다.

**판매처 상세페이지는 원래 세로로 길다.** 비율로 특전 자료를 가려낼 수 없다.

### 프론트에서 무엇을 잘못했고 어떻게 되돌렸나

`render.mjs`에 넣었던 비율 2.4 필터(커밋 `54bf816`)는 특전 이미지 37건 중
**30건(81%)을 지웠다.** 엔하이픈 8건, 코르티스·에반·투바투·튜이드 각 4건이 통째로
사라졌고, 실제로 라이브에 그 상태로 한 번 배포됐다(NCT 상세의 특전 이미지 0개).
판매처가 특전을 공개하지 않는 게 이 사이트의 존재 이유인데 유일하게 확보한
자료를 스스로 지운 셈이다.

진짜 문제는 **표시 방법**이었다. 1:6.14 이미지를 540px 높이 칸에 통째로 넣으면
폭이 88px이라 아무것도 안 읽힌다 — 화면에서 도장처럼 보였던 게 그 때문이다.
지우는 대신 긴 이미지만 **칸 안에서 위아래로 넘겨 보게** 바꿨다(`figure.tall`).

### 남은 교훈

치수·비율 같은 **대리 지표로 내용을 판단하지 마라.** 30건을 지우기 전에
이미지 한 장만 열어봤으면 안 벌어졌을 일이다.

## 3. 메이크스타 이벤트에 포스터 이미지가 없다

### 실측 증거

`out/data/*.json`의 `events[]` 9건 전부, 키 목록에 이미지 계열이 하나도 없다:

```
id, url, type, label, fansign, title, titleEn, album, albumEn, artist,
artistEn, releaseDate, from, to, startAt, endAt, dday, closing, winnerAt,
productId, why, options
```

팬사인회는 앨범값(1~2만원)보다 훨씬 큰 돈이 걸리는 결정인데, 지금은 글자만 있다.

### 프롬프트

```
poc/의 메이크스타 이벤트 수집기가 이벤트 포스터 이미지 URL을 수집하지 않는다.
out/data/*.json의 events[] 객체에 이미지 계열 키가 하나도 없다 (9건 전부 확인).
현재 키: id, url, type, label, fansign, title, titleEn, album, albumEn, artist,
artistEn, releaseDate, from, to, startAt, endAt, dday, closing, winnerAt,
productId, why, options

할 일: src/makestar.mjs에서 https://makestar.co/event/<id> 응답의 대표 이미지
(og:image 또는 이벤트 상세의 메인 포스터)를 뽑아 events[] 각 객체에 `image`
키로 넣어라.
- 절대 URL로 저장할 것 (상대경로면 origin 붙여서)
- 가능하면 {url, w, h} 형태로 치수까지 (rows[].images[]와 같은 모양)
- 못 찾으면 키를 넣지 말 것 — null 대신 부재. 렌더가 존재 여부로 분기한다
- 기존 키는 하나도 바꾸지 말 것

절대 하지 말 것: src/render.mjs는 건드리지 마라. 프론트 담당이 따로 있다.
`image` 키가 들어오면 프론트가 팬사인회 표에 붙인다.
```

## 4. 재빌드가 20분 타임아웃에 걸린다 — 배포가 막힌다

### 실측 증거

`rebuild.yml`의 Build 스텝은 `timeout-minutes: 20`이고 주석에 "정상 빌드는 5~7분"이라
적혀 있다. 그런데 2026-08-27 기준:

| run | 결과 | 소요 |
|---|---|---|
| 33082255907 | success | 8분 24초 |
| 33084113828 | **failure — 타임아웃** | 20분 50초 |
| 33084908700 | success | 20분 40초 (아슬아슬) |

실패한 로그를 보면 **뮤직플랜트가 앨범마다 105초씩** 먹는다(i-dle은 245초):

```
TUIDE  ⏱ Ktown4u 0.5s · 알라딘 0.8s · 사운드웨이브 1.3s · 위드뮤 4.2s
       · 뮤직플랜트 105.3s · 애플뮤직 1.4s · 위버스샵 4.0s
TAEMIN ⏱ … 뮤직플랜트 105.2s …
NCT    ⏱ … 뮤직플랜트 105.2s …
```

13앨범 × 105초 ≈ 23분. 다른 판매처는 전부 1~6초다.

설명이 안 되는 점: `src/musicplant.mjs`는 앨범당 `search_result.php`를 **한 번**만
부르고(파일 73줄, 네트워크 호출은 14행 하나뿐), `fetchx.mjs`의 타임아웃은 15초에
재시도 3회라 최대 45초를 넘길 수 없다. 그리고 한국에서 같은 URL을 직접 치면 **0.42초**다.

빌드가 실패하면 `out/`이 갱신되지 않아 **프론트 변경이 사이트에 못 올라간다.**

### 프롬프트

```
poc/ GitHub Actions rebuild가 20분 Build 타임아웃에 걸려 실패한다. 배포가 막힌다.

증거:
- run 33084113828 실패 (20분 50초), run 33084908700 겨우 성공 (20분 40초).
  정상은 8분대였다 (run 33082255907).
- 실패 로그: 뮤직플랜트가 앨범마다 105초씩 걸린다. i-dle은 245초.
  같은 앨범에서 다른 판매처는 전부 1~6초다. 13앨범 × 105초 ≈ 23분.

설명이 안 되는 점 — 여기부터 조사해야 한다:
- src/musicplant.mjs는 앨범당 search_result.php를 한 번만 부른다 (파일 73줄,
  네트워크 호출은 14행 하나뿐).
- src/fetchx.mjs의 getText는 timeout 15초 + 재시도 3회이고 TimeoutError면
  즉시 break라, 한 호출이 105초가 될 수 없다.
- 한국에서 같은 URL을 curl로 치면 0.42초다.
  → 러너에서 실제로 어디서 시간이 가는지 계측이 필요하다.
    (DNS/TLS인지, 응답 본문이 느린지, 뮤직플랜트가 GitHub IP를 죽이는지)

할 일:
1. 러너에서 뮤직플랜트 호출 구간을 계측해 105초가 어디서 나는지 특정하라.
2. 원인에 맞게 고쳐라. 임시로 타임아웃만 늘리는 건 답이 아니다 —
   13앨범이면 그만큼 그대로 곱해진다.
3. 고치기 전까지 빌드가 죽지 않게 할 방법도 같이 제안하라
   (판매처별 상한, 병렬화, 실패 시 이전 스냅샷 유지 등).

절대 하지 말 것: src/render.mjs는 건드리지 마라. 프론트 담당이 따로 있다.
```

## 넘기지 않은 것

`build.mjs`의 부분 빌드(`--max`, 앨범명 인자)는 **이미 처리돼 있다.**
`PARTIAL` 플래그(274행)로 `gone` 계산을 건너뛰고(426행), 지난 인덱스에서 안 돈
앨범을 되살린다(476행). 예전에 `out/`이 잘렸던 건 `SITE_URL`을 잘못 넘겨서였다.
